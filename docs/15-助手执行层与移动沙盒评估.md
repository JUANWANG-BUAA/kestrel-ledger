# 助手执行层与移动沙盒评估

> 2026-10-17。回答两个问题：DeepSeek Harness（dsh）的设计原理值不值得引入？要不要做 Claude Code 式沙盒？
> 结论先行：**值得引入的是「契约」，不是「运行时」；沙盒要做，但做能力沙盒，不做虚拟机。**

## 1. 现状与差距

当前助手已经具备 dsh 的大部分**上层契约**：

| dsh 概念 | 本应用对应 | 状态 |
|---|---|---|
| 工具注册与调用 | `AgentToolRegistry` + 每轮 allowlist | ✅ |
| 结构化事实 | `AssistantFact`（key/value/unit/source/observedAt/敏感级） | ✅ |
| 可逆副作用 | `AssistantActionProposal` + 二次确认 | ✅ |
| 技能 | `AssistantSkill`（指令 + 工具范围 + 触发词），可 `save_skill` | ✅ |
| 会话工作流 | `AssistantWorkflow` 落盘 SQLCipher | ✅ |
| 长期记忆 | `AssistantMemory` + 词重叠/时间衰减召回 | ✅ |
| 插件动态加载 | 无（不打算做） | — |
| 代码执行 / 文件系统 | 无 | ❌ |

差的是**执行层**：助手能读结构化事实、能提议改账本，但不能把中间结果落盘、不能对数据做多步加工、不能把「一套方法」沉淀成可反复执行的东西。

## 2. 为什么不做 Claude Code 式 VM

Claude Code 的沙盒本质是「一台带工具链的 Linux 机器」：镜像、包管理、进程、网络。搬到手机上代价是：

- 体积：最小镜像 + 运行时通常数百 MB，安装包直接翻十倍；
- 内存/电量：常驻进程与 shell 在后台被系统杀掉，体验不可控；
- 权限面：文件、网络、进程三类权限同时放大，和个人记账 App 的威胁模型不匹配；
- 收益错配：本应用的「计算」是收益、风险、估值，不需要通用 shell。

**dsh 自己也不是 VM**：它是 Host + 插件 + 能力（service/tool/skill）+ 生命周期。可搬的是这种分层，而不是 Node 运行时。

## 3. 推荐：三级能力沙盒

### L1（建议先做）私有虚拟工作区 + 无脚本流水线

- **工作区**：`filesDir/assistant-workspace/`，只允许 UTF-8 文本、CSV、JSON；单文件 ≤ 256 KB，总配额 50 MB，LRU 清理；路径规范化，禁止 `..`、符号链接与绝对路径。
- **工具**：
  - `workspace.list` / `workspace.read`（只读，返回来源、行数、修改时间）；
  - `workspace.write`（写入必须走提案 + 确认，记录审计）；
  - `workspace.query`：对 CSV/JSON 执行**声明式流水线**，不执行代码。
- **流水线 DSL**（在 `:domain` 实现、可单测）：
  ```json
  {"source":"holdings.csv","steps":[
    {"op":"filter","field":"kind","eq":"FUND"},
    {"op":"group","by":"category","agg":{"marketValue":"sum"}},
    {"op":"sort","field":"marketValue","desc":true},
    {"op":"limit","n":8}
  ]}
  ```
  只支持 `filter/select/group/sort/limit/join`，每步有行数上限与超时；模型只生成 JSON，永远不接触执行引擎。
- **收益**：助手可以「把最近 30 天黄金数据导出成 CSV 再看分组」「把估值误差样本整理成表」「把一次分析保存成可复用模板」，而安装包几乎不增长。

### L2（有明确需求再做）受限脚本

- 候选：QuickJS（约 2–4 MB）或小型 WASM 运行时；给 32 MB 堆上限、1.5 秒超时、无网络、无文件系统，只暴露 `workspace` 与 `facts` 两个对象。
- 触发条件：用户需要自定义指标/批量重算，且 L1 的 DSL 无法表达；否则不引入。
- 仍然不放进 APK 的默认路径：作为可选下载模块，缺失时功能降级。

### L3（不做）通用 VM / shell

- 无终端、无包管理、无任意网络、无后台常驻进程。

## 4. 安全模型（比功能更重要）

| 面 | 规则 |
|---|---|
| 能力 | 每轮工具 allowlist；写类工具额外要求「允许修改本机数据」总开关 |
| 路径 | 规范化后必须位于工作区根内；拒绝符号链接、隐藏路径、设备文件 |
| 配额 | 单文件 256 KB、总量 50 MB、每轮读写 1 MB；超限返回稳定错误码 |
| 执行 | DSL 有行数/步数/时间上限；禁止递归、禁止外部 IO |
| 网络 | 只有 `web.fetch` 白名单主机，工作区工具不联网 |
| 数据分级 | 行情公开；持仓/流水私密，默认不进入工作区；写工作区视为本机数据，不进备份除非显式导出 |
| 审计 | 每次写/删记录时间、来源工具、大小、摘要；工作区可一键清空 |
| 提示注入 | 网页/文件内容一律标记为「数据」，工具返回不提升为指令；系统提示固定声明 |

## 5. 与现有代码的落点

- `:domain`：`WorkspacePath`（规范化）、`PipelineSpec` 解析与执行、`WorkspaceQuota`；
- `:data`：`LocalWorkspace`（文件 IO + 配额 + 审计）、`WorkspaceAgentTool`；
- `:app`：设置页「工作区」入口（用量、清空、近期文件）、提案确认卡片复用；
- 不新增权限、不新增后台进程、不改变备份格式（工作区默认不进账本备份，另提供导出）。

## 6. 建议顺序

1. 工作区读写 + 配额 + 审计（L1-a）；
2. 声明式流水线 + 单测（L1-b）；
3. 把图表/报告模板接到工作区（模型只选配方，不拼代码）；
4. 视需求评估 QuickJS 可选模块（L2）；
5. 动态插件市场：不做。技能已经覆盖「用户自定义能力」，插件带来的权限与供应链风险不值得。

> 一句话：**dsh 的契约已经抄过来了，缺的是给它一个安全、小体积、可审计的执行面。**
